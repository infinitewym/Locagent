## 背景

全量评测：`uv run locagent-eval --trials 3`，共 12 个任务，结果在 `artifacts/evals/20261016-090841`。

- 36 次试验通过 33 次（92%）。回归题 18/18 全过，8 个旧任务没有退步。
- 上次的修复都已生效：
  - long_file_write 不再被截断，平均耗时从 436 秒降到 302 秒。
  - 所有最终回答都是中文。
  - 共触发 5 次收尾请求，都没有再调用工具。

逐条读会话记录后，发现 4 个问题。

## 问题 1：步数用完时，没做完的任务被记成"已完成"

**现象**

rename_config_key_large 三次都用满 25 步。收尾时，模型按要求不再调用工具，给出的回答是"已完成部分修改，但由于工具预算耗尽，无法继续完成……需要修改的剩余文件包括 services/cache.py……"。但会话记录里，这次运行被记成 `status=completed`、`stop_reason=final_answer_returned`，检查点状态也是 completed。

后果：

- 交互使用时，命令行不会提示"任务未完成，输入 /continue 接着做"，/continue 也会报"没有未完成的任务"。
- 评测时被统计成"声称完成但判分失败"（false completion）。但模型其实如实说明了没做完，算它"声称完成"是冤枉的。

**原因**

`agent_loop.py` 的 `_loop()` 在发出收尾请求后，只要模型返回了文字，就按"正常给出最终回答"处理，返回 `STATUS_COMPLETED, STOP_REASON_FINAL_ANSWER`。收尾请求本来就是被步数上限逼出来的，回答的内容通常是"做到哪了、还剩什么"，不代表任务完成。

这个问题以前就存在。上次给收尾请求加了 `tool_choice: none` 之后，收尾一定会得到文字回答，所以现在每次步数用完都会走到这条错误的路径。

**修改**（`locagent/agent_loop.py`）

收尾请求得到文字回答时，仍然把这段文字作为最终回答（命令行照常显示），但返回 `STATUS_STOPPED, STOP_REASON_STEP_LIMIT`。修改后：

- 检查点状态是 stopped，停止原因是 step_limit_reached，命令行会提示可以 /continue。
- 评测中这类试验的失败类型是 `step_limit_reached`，不再算作 false completion。

## 问题 2：update_todos 占用工具步数

**现象**

rename_config_key_large 第 1 次试验的 25 步里，有 9 步是 update_todos：模型每改完一个文件，就单独发起一次请求，只为了把清单上的一项打勾。第 2、3 次试验各有 5 次。每次打勾除了占一步，还要多一次模型请求。

**原因**

步数上限的本意是限制 agent 对工作区的操作次数（读、写、搜索、运行命令），防止它一直做下去。update_todos 只更新内存里的待办清单，不读写工作区，却和其他工具一样计数。结果模型越认真维护清单，真正能干活的步数就越少。

**修改**（`locagent/agent_loop.py`）

- 新增常量 `BOOKKEEPING_TOOLS = ("update_todos",)`。
- 计算步数上限时，不统计这些工具的调用。
- 运行统计里的 `tool_steps`（会话记录的 run_finished 事件、评测报告里的 steps）也改用同样的口径，避免出现"步数超过上限"的显示。
- 检查点的 `record_step` 本来就跳过 update_todos，三处口径现在一致。

防止无限循环由 `max_attempts`（模型请求次数上限，等于步数上限的 3 倍）保证。即使模型只调用 update_todos，也会在请求次数用完后以 retry_limit_reached 停止。

## 问题 3：rename_config_key_large 的步数上限给少了

**现象**

即使不算 update_todos，这个任务按合理的做法也需要：

- 搜索 1 步；
- 13 个文件各读一次、改一次，共 26 步；
- 运行测试和 main.py，共 2 步。

合计约 30 步，而上限只有 25。

**原因**

出题时没有按合理做法估算步数。Anthropic 的评测指南要求，每个任务都应该能被一个按要求正确操作的 agent 完成。这个上限让任务变成了不可能完成，测不出能力。

**修改**（`evals/tasks/rename_config_key_large/task.json`）

`max_steps` 从 25 改为 35，`source` 字段记录了修改原因。

## 问题 4：patch_file 因为中文引号匹配不到

**现象**

implement_parse_duration 三次试验都至少出现一次 `old_text must occur exactly once, found 0`。duration.py 的文档字符串里是中文引号："由一段或多段“非负整数 + 单位”组成"，模型写 old_text 时把它写成了英文引号 `"非负整数 + 单位"`，于是匹配不到。模型只能重新读文件、再试一次，每次多花 1 到 2 步。

**原因**

模型抄写原文时，会把中文引号、全角符号、空格或缩进"规范化"。这种差别肉眼很难看出来，原来的报错只说"找到 0 处"，没有告诉模型差在哪里。

**修改**（`locagent/tools.py`）

patch_file 找不到 old_text 时（并且不是行号前缀的问题），在 old_text 里找出第一行不在文件中的内容，用 `difflib` 在文件里找出最相近的一行（相似度不低于 0.6），把两者并排写进错误信息：

```
old_text must occur exactly once, found 0; this old_text line is not in the file: '    """由一段"非负整数 + 单位"组成"""'; closest file line 2: '    """由一段“非负整数 + 单位”组成"""'
```

这样模型一眼就能看出是引号不同，下一步直接改对，不用重新读文件。

这里只是给提示，不做模糊匹配：修改仍然要求 old_text 精确命中，修改行为保持确定。

  - 2 次放弃 patch_file，改用 write_file 重写整个文件，顺带把文档字符串里的中文引号“”都换成了英文引号。
  - 1 次重新读文件，再试一次。

  看起来模型很难原样写出中文引号，所以"告诉它差在哪里"还不够。

## 后续建议

1. 修改 4 的提示再加一句：如果没法原样写出这一行，就换一段不包含这一行的更短的 old_text（例如只替换 `raise NotImplementedError`）。这样模型不必再写出中文引号，也就不会为了绕开它去重写整个文件、改坏原文。
2. rename_config_key_large 的上限可以考虑调到 40，让"每个文件先读再改"这种同样合理的做法也能做完。
3. 修完后再跑一次全量 `--trials 3`，确认 12 个任务都没有退步。
