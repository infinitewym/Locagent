# 评测问题修复记录（2026-10-15）

## 背景

第一次基线评测：`uv run locagent-eval --trials 3`，结果在 `artifacts/evals/20261015-202027`。

- 24 次试验通过 23 次（96%），回归题 18/18 全过。
- 问题集中在 long_file_write：3 次试验都把 10 步用满，平均输入 8.7 万 token，是其他任务的 4 到 17 倍。其中 1 次因为步数用完失败。

逐条读了这 3 次的会话记录，每次只有约 4 步在干活，另外约 6 步浪费在下面这些问题上。所以不是步数上限给少了，是 LocAgent 本身有 bug。调大上限只会把问题藏起来。

## 问题 1：run_shell 的多行命令在 Windows 上没执行，却显示成功

**现象**（3/3 次出现）

模型写了这样的命令：

```
python -c "
lines = ['ROWS = [']
for n in range(1, 801):
    ...
"
```

返回结果是 `exit_code: 0`，stdout 和 stderr 都是空的，但文件并没有生成。模型以为成功了，接着去读文件，提示文件不存在；再用 list_files 确认，再换成 exec 写法，又报错。每次试验因此浪费 3 到 4 步。

**原因**

Windows 上 run_shell 通过 cmd.exe 执行命令。cmd.exe 把换行当作命令结束，只执行第一行 `python -c "`。Python 收到的是一段空程序，正常退出，退出码为 0，后面几行全部被丢掉。

**修改**（`locagent/tools.py`）

- `validate_tool` 中，Windows 上的命令只要中间带换行，就在参数校验阶段直接拒绝。错误信息是："cmd.exe runs only the first line of a multi-line command; write the code to a .py file with write_file, then run it with python"。
  - 这一步在审批之前：执行不了的命令不会弹出审批，也不会真的运行。
  - 命令末尾多一个换行不算多行，照常执行。
  - Linux 的 sh 能正常执行多行命令，所以不受影响。
- run_shell 的工具说明改为 "single-line shell command"，并写明多行代码要先用 write_file 写成脚本再运行，让模型一开始就不这样写。

这里的思路是让这种情况不再发生（不让静默失效的命令进来），而不是事后补救。

## 问题 2：输出被截断时没有识别出来

**现象**（2/3 次出现）

模型的第一次回复就想用 write_file 一次写完 800 行，输出写到 8192 token 上限就停了。会话记录里这次回复的 `stop_reason` 是 `tool_use`，工具参数变成了 `{"raw_arguments": "{\"path\": \"squares.py\", \"content\": \"ROWS = [...`（一段写了一半的 JSON），工具报错 `invalid arguments for write_file: 'path'`。

**原因**

按 Anthropic 接口的约定，输出写满上限时 `stop_reason` 应该是 `max_tokens`。主循环在第 4 步已经为这种情况准备了处理：丢弃被截断的回复，提示模型分段写（TRUNCATED_NOTICE）。但百炼的兼容接口在输出写满时仍然返回 `tool_use`，所以这个处理从来没有触发。半截的参数被当成正常的工具调用，交给执行器后报出一个看不懂的错误（`'path'` 是 KeyError 的原始文字）。

**修改**（`locagent/providers/qwen.py`）

拿到返回结果后，如果 `output_tokens >= max_new_tokens`，就把 `stop_reason` 改成 `max_tokens`。

这是百炼接口和标准不一致的地方，所以在对接接口的 qwen.py 里纠正，主循环不用改。改完后，主循环原有的截断处理就能接上：丢弃截断的回复，记一条运行时提示，让模型先用 write_file 写第一部分，再用 patch_file 续写。

## 问题 3：步数用完后，模型还在调用工具

**现象**（1/3 次出现）

trial 1 用满 10 步后，主循环发出收尾请求，附带提示 "the tool budget is exhausted. Do not call another tool..."。模型没有理会，又调用了一次 run_shell。结果是 `step_limit_reached`，判分失败。实际上这时 squares.py 已经正确生成，判分脚本是能通过的。

**原因**

收尾请求只是用文字要求模型别调用工具，并没有在接口层面禁止。

**修改**

- `providers/qwen.py`：`complete()` 增加参数 `tool_choice`，有值时放进请求。
- `providers/clients.py`：假模型的 `complete()` 同步增加这个参数，并把它记录到 `requests` 里，方便检查。
- `runtime.py`：`request_model(tool_choice=None)` 把这个参数往下传。
- `agent_loop.py`：收尾请求传入 `NO_TOOLS = {"type": "none"}`，在接口层面禁止调用工具。

为什么不直接去掉 tools 参数：历史消息里已经有 tool_use 和 tool_result 块，按 Anthropic 接口的规定，这时请求必须带上 tools，否则会被拒绝。所以只能用 `tool_choice` 来禁止。

**待确认**：百炼兼容接口是否支持 `tool_choice: none`。验证方法：用 `--max-steps 1` 跑一个需要多步的任务，最后一次请求应该直接给出文字回答。如果接口报错或者不生效，就撤掉这一项。

## 问题 4：long_file_write 任务没测到目标能力

**现象**

这个任务本来想考"输出太长时分段写入"，但开放了 run_shell。3 次试验里，模型最后都写了一个生成脚本，用 Python 生成 squares.py。产出的文件符合要求，判分正确地给了通过，但分段写入这个能力根本没被考到，工作区里还多出了 gen_squares.py 和 generate.py。

**原因**

任务设计问题：开放的工具允许绕开要考的能力。

**修改**（`evals/tasks/long_file_write/task.json`）

- 增加 `"allowed_tools": ["list_files", "read_file", "write_file", "patch_file"]`，不开放 run_shell。
- `source` 字段补充了修改原因。

改完后，模型只能直接写出 800 行，必然会遇到截断，正好用来检验问题 2 的修复。

## 顺带说明：不算问题的工具失败

fix_failing_test 平均每次有 2 次工具失败：

- 一次是修复前先运行测试，测试本来就会失败（`command_failed`，属于预期结果）。
- 一次是 patch_file 的 old_text 匹配到了两处，被拒绝后模型补了上下文重新改。

这两次都是正常过程，不需要修改。


对比基线时注意：long_file_write 现在不开放 run_shell，变成了一道更难的题，分数和基线不能直接比。重点看两点：

1. 每次截断是否都触发了截断提示（会话记录里出现 notice 事件，`model_responded` 的 `stop_reason` 是 `max_tokens`），之后模型是否改为分段写。

## 重跑结果（artifacts/evals/20261015-220029）

命令：`uv run locagent-eval --tasks long_file_write --trials 3`

| 指标 | 基线（20261015-202027） | 修复后 |
|---|---|---|
| 通过 | 2/3 | 3/3 |
| 平均工具步数 | 10（每次都用满） | 5.3（8 / 4 / 4） |
| 平均工具失败 | 2.7 | 0 |
| 截断被识别 | 0/2 | 3/3 |
| 平均输入 token | 86,515 | 61,188 |
| 平均输出 token | 6,341 | 25,085 |
| 平均耗时 | 119 秒 | 436 秒 |

注意：修复后这个任务不开放 run_shell，模型只能自己把 800 行写出来，不能用脚本生成，所以输出 token 和耗时上升是题目变难的结果，不能和基线直接比。可以直接比的是"截断是否被识别""是否还有无效步骤"。

各项修复的验证情况：

- **问题 2（截断识别）：已验证。** 3 次试验的第一次回复都想一次写完，输出到 8192 token 被截断。会话记录里 `stop_reason` 都是 `max_tokens`，随后出现截断提示（notice），模型改为先 write_file 写第一段，再用 patch_file 一段一段续写。整个过程没有一次工具失败。
- **问题 4（任务修正）：已验证。** 模型不能再用生成脚本绕开，工作区里也不再多出生成脚本。
- **问题 1（多行命令）：这次没有触发。** 任务不开放 run_shell，要在 fix_failing_test、expense_multistep、rename_across_files 等任务里观察。
- **问题 3（tool_choice none）：这次没有触发。** 没有一次用满步数，百炼是否支持还需要单独验证。

重跑中发现的新现象：

1. **第一次回复白白浪费。** 3 次试验都先尝试一次写完，被截断后整段丢弃，每次浪费 8192 个输出 token、约 140 秒，大约占总耗时的三分之一。原因是模型不知道单次输出有上限。可以在 system prompt 里写明单次输出上限，以及"长文件分段写"，让模型从第一次就分段写。
2. **回答语言变了。** 截断提示是英文的，模型之后的说明和最终回答都改用英文，而用户是用中文提问的。可以在规则里加一句"用用户的语言回答"。
